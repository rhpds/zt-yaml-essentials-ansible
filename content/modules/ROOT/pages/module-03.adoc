= 3. Variables & Best Practices

== Introduction

Variables make your Ansible playbooks flexible and reusable. Instead of hardcoding values throughout your playbook, you define them once and reference them wherever needed.

In this module, you will:

* Learn how to define variables in playbooks
* Use variables in tasks with Jinja2 syntax
* Write effective comments for documentation
* Apply YAML best practices

== Why Use Variables?

Variables provide several benefits:

* *Reusability:* Change a value once instead of in multiple places
* *Flexibility:* Easily customize playbooks for different environments
* *Readability:* Meaningful variable names make code self-documenting
* *Maintainability:* Centralize configuration values

== Hands-On Experience

======
.☑️ Task 1 - Add variables to your playbook
[%collapsible]
=====
NOTE: In the *VSCode Editor* tab

. Update `site.yml` with variables:
+
[source,yaml]
----
---
- name: Configure web servers
  hosts: webservers
  become: true
  vars:
    web_package: httpd
    web_service: httpd
    http_port: 80

  tasks:
    - name: Ping all web servers
      ansible.builtin.ping:

    - name: Install web server package
      ansible.builtin.package:
        name: "{{ web_package }}"
        state: present

    - name: Start and enable web service
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true
----
+

IMPORTANT: Variables starting a value must be quoted: `"{{ var }}"` not `{{ var }}`
=====
======

=== Variable Naming Conventions

Follow these best practices for variable names:

* Use lowercase with underscores: `http_port`, `max_clients`
* Make names descriptive: `web_package` not `pkg`
* Avoid starting with numbers: `port_80` not `80_port`
* Be consistent with casing throughout your playbook

.☑️ Task 3 - Use variables with lists (loops)
[%collapsible]
=====
NOTE: In the *VSCode Editor* tab

. Update `site.yml` to use a list variable with loop:
+
[source,yaml]
----
---
- name: Configure web servers
  hosts: webservers
  become: true
  vars:
    web_packages:
      - httpd
      - mod_ssl
      - firewalld
    web_service: httpd
    http_port: 80

  tasks:
    - name: Ping all web servers
      ansible.builtin.ping:

    - name: Install web server packages
      ansible.builtin.package:
        name: "{{ item }}"
        state: present
      loop: "{{ web_packages }}"

    - name: Start and enable web service
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true
----

== Adding Comments

Comments make your YAML files more maintainable by explaining why decisions were made, documenting complex logic, or marking TODOs.

=== Comment Syntax

YAML comments begin with `#`. Everything after `#` on a line is ignored:

[source,yaml]
----
# This is a full-line comment
vars:
  http_port: 80  # This is an inline comment
----

======
.☑️ Task 4 - Add comments
[%collapsible]
=====
NOTE: In the *VSCode Editor* tab

. Add comments to `site.yml`:
+
[source,yaml]
----
---
# site.yml - Web Server Configuration Playbook
#
# This playbook configures Apache web servers with SSL support
# and firewall configuration for the TechStart Inc. infrastructure.
#
# Target: webservers group from inventory
# Requirements: RHEL 9 with network connectivity

- name: Configure web servers
  hosts: webservers
  become: true  # Required for package installation and service management

  vars:
    # Package list includes Apache, SSL module, and firewall
    web_packages:
      - httpd        # Apache web server
      - mod_ssl      # SSL/TLS support
      - firewalld    # Firewall management

    web_service: httpd
    http_port: 80    # Standard HTTP port

  tasks:
    # Connectivity test - ensures Ansible can reach all hosts
    - name: Ping all web servers
      ansible.builtin.ping:

    # Install all required packages in a single task
    - name: Install web server packages
      ansible.builtin.package:
        name: "{{ item }}"
        state: present
      loop: "{{ web_packages }}"

    # Ensure web service is running and enabled at boot
    - name: Start and enable web service
      ansible.builtin.service:
        name: "{{ web_service }}"
        state: started
        enabled: true  # Start automatically on system boot
----
+
=====
======

=== Comment Best Practices

[cols="1,2",options="header"]
|===
|Practice |Example

|Document why, not what
|`# Using port 8080 to avoid conflict with existing service`

|Keep comments up-to-date
|Update comments when you change code

|Use comments for playbook headers
|Document purpose, author, requirements

|Explain complex variable structures
|Describe what nested dictionaries represent

|Mark TODOs
|`# TODO: Add SSL certificate configuration`
|===

== YAML Best Practices Summary

Here are the key best practices you've learned:

[arabic]
. *Start files with `---`* to mark YAML document beginning
. *Use 2 spaces for indentation* - never tabs
. *Maintain consistent casing* in variable names
. *Quote strings that start with variables* - `"{{ var }}"`
. *Use descriptive variable names* - `web_package` not `pkg`
. *Add meaningful comments* for documentation
. *Use `true`/`false`* for boolean values
. *Avoid unnecessary quotes* on simple strings
. *Keep playbooks readable* with blank lines between sections

== More Boolean Examples

You've seen `become: true` and `enabled: true`. Here are other common boolean uses in Ansible:

[source,yaml]
----
gather_facts: false        # Skip automatic fact gathering
check_mode: true          # Run in dry-run mode
ignore_errors: true       # Continue even if task fails
changed_when: false       # Never report as "changed"
----
